# OpenLookout 解决实测报告（混合真实数据）

针对用户反馈：

1. **怕像软件提醒一样烦** → 只要更少的、已经做好的卡片  
2. **自己录一天可能没东西** → 用多周、带真实表格的开源数据  
3. **发现问题不够** → 必须真正解决经常发生的麻烦活  

本轮不再只做「镜子式观察」，而是端到端跑：**发现 → 拼/生成解决办法 → 在真实文件上验证 → 只上已办清单**。

## 2. 经常发生的麻烦，怎么真正解决？

原则：**不操控鼠标**。积木只读写文件 / 生成脚本 / 写未发送草稿；付款、提交、外发永远要用户自己按。

| 重复麻烦 | 怎么解 | 验证 |
|---|---|---|
| 每周五从明细+类别对照手工拼周汇总 | 按上周版面从源表按日期汇总（LLM 拼装失败或验证 <85% 时回退确定性流程） | 7 周共 112 格，**108 格一致**；不一致的 1 格可解释 |
| 手工周报算少了 | 验证时顺带重算，生成正确版周报 | 2024-09-20「本周支出合计」手工 13055.53 vs 源表 13338.42（差 282.89，对应专项津贴少计） |
| 订阅同日双扣 | 确定性核对账单 → **退款申请草稿**（不发送） | 两笔订单号不同、间隔 41 秒；往月每月一笔 |
| 订阅涨价 | 生成**订阅扣费清单.xlsx** | 80 → 95（+19%），金额源自公开表中的 Petty Cash 字段 |
| 截止日要交「差旅补贴+凭票报销」预算表 | 从费用明细按关键词筛行 → `task_sheet.xlsx` | 写出 560 行相关记录（确定性，不跑鼠标） |
| 明细往 OA 表单粘贴 | 抽出待填行 + 填写说明（**不提交**） | 已验证；因每日上限 5 张压进抽屉（去打扰） |

窗口来回撕扯、纯观察：**直接省略**，不上清单。

## 3. 去打扰怎么落地

`real_data/run_solve.py`：

- 每日主卡上限 **5**  
- 价值分 < 12 不入选  
- 截止日 > 14 天不入选  
- 状态为 `omit` / 无成品的 draft / 纯 reminder → **沉默抽屉**  
- 只有 `verified`，或「带真实文件的 draft」才写卡片  
- 观察类（window_thrash 等）默认不打扰  

本轮结果：检测 9 条 → 入选求解后上卡 **5**（全是 verified）→ 沉默 5（含 1 张已验证但超日限额的待填报销行）。

## 5. 模型与成本（本机实测）

- 判断 / 写卡：`mimo-v2.6-flash`  
- 拼周报工作流：`mimo-v2.6-pro`（验证差则回退确定性，本轮触发了 `llm_match_17/112_to_deterministic`）  
- 调用 **3** 次，约 **7787** tokens，端到端约 **95** 秒  
- Key 只读 `~/.config/ai-butler/mimo.env`，不打印  

---

## 6. 诚实的边界

1. 活动轨迹是重建的，不是某个真人一周的录屏；惊喜建立在「真实数字的文件 + 合理的重复劳动模式」上。  
2. 周报 LLM 一次拼装只有 17/112 格对上，**靠本机验证 + 确定性回退**才交付；说明「积木拼装」仍需要强验证，不能盲信模型。  
3. 微信服务号提交、封闭 App 点鼠标仍不在范围内；对外动作只做到草稿/待填。  
4. 截止日筛出 560 行是「含关键词的历史明细」，不是财务制度意义上的正式预算表——卡片应被当成「已经帮你筛好了素材」。
