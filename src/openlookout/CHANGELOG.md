## 第 11 轮：从"机会卡"到"机会发现 + 第一步实测"
- 新增 `lookout/opportunity_engine.py`（`python3 -m lookout.opportunity_engine --profile … --signals … --out … [--llm] [--from-response …]`）：
  - 先删掉画像里的排除主题，再做出站审计（URL、路径、邮箱、长数字都会被拦）。
  - 确定性交叉匹配：词表把画像映射成资产标签；用"优势映射"判断哪条外部信号奖励哪些资产；稀缺度按资产家族计算，近义标签不重复加分。只有一条信号同时奖励组合里的全部资产才算命中，不把无关信号拼成一个主题。
  - 可选让 mimo-v2.6-pro 写机会卡，发给模型的信号不带 URL。返回后做硬校验：引用的信号 id 必须存在；依据里出现的 ≥3 位数字必须能在所引信号原文里找到；资产必须能映射回画像；至少涉及 2 个资产家族；不得出现排除主题；第一步要有可测量的验收标准。模型偶尔会多吐一个括号，用宽松解析兜底，`--from-response` 可以离线重放。
  - 测试：`opportunities/tests/test_engine.py`。信号样例 `opportunities/signals/2026-10-09.json` 共 20 条，都是当天打开原页面核对过的公开事实，每条带 URL 和日期。
- 新增 `opportunities/dual-migration-cbom/`（`dmcbom.py`，只用标准库；做 schema 校验需要 jsonschema）：
  - 扫源码里的密码使用。每条发现标两条轴："是否国密"和"量子影响"，结论分 L/D/G2/OK/S/P 六类。G2 指"已经是国密，但仍要做抗量子的第二次迁移"。
  - 输出 CycloneDX 1.6 CBOM，用仓库里自带的官方 schema 校验；同时输出中文迁移清单。
  - Python 用 AST 解析，带导入别名和赋值别名传播；Go、JS、Java、C 用"导入绑定 + 使用点"匹配；还能识别配置文件里的国密 TLS 套件。
  - 区分调用点、类型引用、自实现和自称的非安全用途（`usedforsecurity=False`）。
  - 测试有 8 个，多语言夹具按"文件:行:算法"逐条比对。`eval/run_eval.py` 在 16 个公开仓库上评测，结果写进 `eval/RESULTS.md`，人工抽检记录在 `eval/AUDIT.md`。
- 修过的误报和漏报（都是从真实仓库的输出里发现的）：
  - JS 字符串和对象键里的 `sm2` 被当成调用；
  - `smx509.Certificate` 和 gmtls 类型被当成 SM2；
  - Go 子包前缀误匹配，比如 `gmcredentials/echo`；
  - Python 的包装函数和 GUI 函数被当成自实现；
  - Java 类名的行号差 1；
  - 懒加载别名漏报；
  - 嵌套类导入、BCEC 密钥类和 RC2 漏报。
- 实测（16 个仓库，499 个文件，约 1.1 秒）：
  - 581 条发现，其中调用点 267 条；国密相关 278 条；
  - 国密调用点里有 92/130 落在 CBOMkit 文档覆盖范围之外；
  - 16/16 个仓库的 CBOM 通过 schema 校验；对照组的国密误报为 0。
  - 人工留出抽检精确率 59/60；文件级召回 11/14（修复前测的）。
- 已知不足：
  - 对手覆盖是按 README 和源码 grep 推断的，没有实跑 SonarQube；
  - 评测仓库是自己挑的，抽检人就是作者；召回没达到 90% 的目标；
  - 不追调用图，类型引用会让计数偏多；
  - 引擎的词表是手写的；LLM 看到了确定性主题，所以它的结论和确定性结果一致，不算独立印证。

## 第 9 轮：第一次跑真实用户的 Windows 历史回溯（90 天）
- 数据是用户本人的，只在本机：采集目录、成品和私有演示都写进 `.gitignore`，没有提交。发到云端的只有统计描述（2 次 flash 调用），出站审计会拦截人名、文件名和长数字，`outbound/` 里查过没有人名、路径和文件名。
- **噪声来源**：九千多条事件里有三千多条来自应用内嵌浏览器和自动化浏览器（游戏平台、代理客户端、桌面 App 的 WebView，自动化测试浏览器，抓包工具自带的浏览器），旧版都叫 "default"，分不清是谁。`backfill_win` 现在把它们标成 `appshell-*` / `automation-*`；`lookout/history.filter_noise` 直接丢掉这两类，旧版的 "default" 也整体丢掉。另外丢掉 localhost 这类本机开发页面和浏览器内部页。结果是 9155 条里留下 5211 条。
- **解析**：Windows 记事本存的 GBK / UTF-16 文本以前直接让 `detect_deadlines` 崩溃。现在用 `common.read_text_any` 读，依次试 utf-8 / utf-16 BOM / gb18030，也能读 docx 的段落和表格。应用缓存目录（Service Worker、CacheStorage 等）不再当成用户写的文件。脱敏会扫工作簿里所有工作表的“姓名”列，以前只看活动表，一周一张表的工作簿会漏掉人名。
- **去掉的垃圾**：
  - `recurring_doc_focus` 在回溯模式下跳过。原因是 dur_s 是标签页开着的时长，不是用户在看它的时间，真实数据上产出的几十条都是一直开着的网页。
  - 重复查询不再算两种情况。一是导航式搜索：搜一个词后，去的站点名或标题里就含这个词，比如搜站点名再点进去。二是 `reload` 型访问，也就是浏览器重启后恢复标签页，看起来像每天早上又搜了一次。
  - 无空格的产品名也不再按“实体+属性”归成一类。
  - `site_rhythm` 忽略浏览器自己打开的页面（`toplevel`，比如更新后弹出的更新日志）。不按星期集中时，描述改说“每 N 天”。
  - 重复下载的副本如果已经全删了，就不出成品。
- **新增（通用，不针对这份数据）**：
  - `lookout/sheet_audit.py`：识别“多张同表头明细表 + 一张没有公式的汇总表”，按明细重新加总后逐格比对。会尝试“每 k 次 A 折成 1 次 B”这样的折算规则来解释差异，只有它解释的行数 ≥3、占 ≥60%，而且不弄坏原本对得上的行，才采用。成品是新工作簿：原表不动，加“自动汇总(公式)”和“差异核对”两张表。验证用 LibreOffice 无界面重算，再和 Python 独立加总逐格比对，同时检查原工作表逐格没变。同结构的几个工作簿合成一条。
  - `history.detect_numbered_series` + `lookout/series_kit.py`：识别“同一父目录下编号连续的子文件夹”这类系列任务，看每期留了几个报告文件、命名写法有几种，并推测下一期。成品是每期文件清单和一个开新一期的脚本（默认只演示，不覆盖已有文件）。验证方法是用历史文件名在沙箱里逐期回放。
  - `history.detect_duplicate_copies`：同名同大小的文件出现在多个文件夹。通常是故意放两处，所以只记录。
- **去打扰**：回溯模式也改成只有 verified，或带成品的 draft 才上清单。只做了提醒的（reminder_only）进抽屉。`--max-cards` 真正生效。新增 `--prepared`，把成品另拷一份。卡片标题对有模板的类型一律用确定性模板。原因是 flash 把“解释不了的格数”当成“对不上的格数”写进了标题，还把占位符的类型标注抄进了正文；后者现在会被清掉。
- 回归：`backfill_win/tests` 全部通过，新增了浏览器来源标签的检查。假数据回溯能跑通，site_rhythm 只做了提醒、不再上卡，这是有意的改动。模拟数据上检测器的产出和原来一样。

## 第 0 轮：只跑检测器，不调模型
- 找到 22 条发现。噪声很多：订单号这一列被当成在漂的数值（4 条）；同一批行因为"类型=对照"和"试剂=柠檬酸钠"两个分组重复报了 2 次；在知网反复搜同一篇文献的主题被算成"重复查询"（5 条）；"NaBH4 分子量"和"硼氢化钠 摩尔质量"被拆成了两类；星期显示有错位（周五显示成周四）；周期算出来是 6.5 天。

## 第 1 轮：修检测器，第一次端到端跑通（flash）
- 漂移检测排除编号型数值列（几乎每行都不一样的整数或长数字），分组按"行集合"去重，起点改成"第一个超出 3 倍标准差的点"。
- 重复查询加一个"停留时间"条件：中位数超过 180 秒算在阅读，不算查答案。搜完粘贴了同一个值的不同说法，合并成一类，靠的是"答案相同"，不是词典。
- 星期的索引错位修好；间隔改成按小时四舍五入成天数。同一句话里有两个日期时，只保留最近的那个截止日。
- 结果：发现 8/9，上卡 6/9，验证通过 5/9，没有误报。**最关键的周报失败了**：模型把表格引用写成了单元格地址 "A10"，平均值也只保留了 2 位。另外速查表把"映射"直接交给了写表积木；送样表的验证器没跳过标题行（这是我的 bug）。

## 第 2 轮：积木和提示词
- 每块积木的说明写清楚"参数必须是 '$步骤id'"，校验器会检查参数名和引用。积木对常见的"差一点对"的输入更宽容（`{columns, rows}`、映射）。新增 `map_to_table` 积木，因为模型反复用 python_transform 干这件事，说明积木库缺这一块。
- 发给模型的报告版面里写明小数保留几位、统计周期的格式。
- 沙箱跑不通时，把脱敏后的报错交回模型修一次（自我修复）。
- 写卡片的提示词：禁止出现内部代号（第 1 轮卡片里出现了"文档组D与P"）；先说"这对你意味着什么"；按钮里的占位符也在本机填。涨价卡之前什么文件都没准备，违反了"已经做好"的原则，改成生成订阅扣费清单。
- 结果：上卡 7/9，验证通过 7/9。周报连续两次因为 **JSON 少一个右括号**而失败。

## 第 3 轮：解析容错 + 真实记录器的问题
- 解析 JSON 时按括号栈补齐少掉的右括号，只补结构，不改内容。
- 用离线回放检查：模型之前输出的周报工作流，补齐括号后在沙箱里能对上 62/63 格，还自己找到了 9/18 那份周报的错。
- 漏掉的那一行如果有两条候选（金额都是 200），卡片会如实说"没法确定是哪一条"，不硬猜。
- 发现了我自己的校验器 bug：`write_xlsx_report` 的 table 参数本来就是字典，却被当成"必须是 $引用"，导致合法的工作流被拒。
- 接入队友的真实记录器：事件按时间重排（记录器在离开窗口时才写 focus 事件）；剪贴板事件没有原文时不崩溃；**inotify 新建文件时会先报一次 IN_OPEN**，原来"之前没打开过才算新建"的规则在真实数据上会把所有新文件漏掉，改成"保存前 60 秒内的打开算作新建本身"。

## 第 5 轮：flash 和 pro 的对比暴露出验证器和脱敏的漏洞
- pro 写的税额正则里带了"超纯水桶"四个字。这是发票明细里的商品名，脱敏模板没有把它遮掉，结果正则只对那一张发票有效。**本机验证抓到了这个问题**：40 个历史字段只对上 35 个，所以卡片降成了草稿。
- 但是无头浏览器的 DOM 测试没抓到：它只数"找到了几个输入框"，没检查框里有没有值。现在改成"框里必须真的有值"。
- 脱敏补了两个洞：发票明细行（商品名、规格）整行遮掉；人名词典之外的人名（比如"开票人：孙强"）按"角色：值"的格式遮掉。**之前 8 次调用的出站内容里出现过一个开票人的名字**（模拟数据里的人名，不是用户本人）。
- 写卡片的提示词：东西已经做好时，问题改问"以后要不要自动做"，不再问"要不要现在生成"。占位符旁边标上类型（数字、日期、文件名），因为模型曾把日期当成份数用（"过去 2026-09-18 份报告"）。
- 新增 `lookout/rewrite.py`：只重跑写卡片这一步，改文案时不用重跑整条流水线。
