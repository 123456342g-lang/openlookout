# OpenLookout 项目现状与方向判断

> 撰写日期：2026-10-13
> 面向对象：项目负责人
> 依据：`STATUS.md`（历史看板）、`sprite_home/perceive/*.jsonl`（真实运行账本）、源码实际调用路径、本机测试实跑

## 0. 一句话结论

**它现在是一个"会读屏幕、会查资料、会写文档的旁观者"，不是助手。**
主动开口这个能力是真的（3 天 78 句），但「帮上忙」这个能力**从未在真实数据里端到端成立过一次**。
项目内部最诚实的一份文档 `docs/strategy/05-measured-reality.md` 其实已经写出了这个结论，
但根目录 `STATUS.md` 的叙述口径仍然是「已完成 / 已打通」。

**诚实完成度：约 35%**（依据见 §6）。

### 2.2 诚实的判断

| 维度 | 结论 | 依据 |
|---|---|---|
| 对一个真实用户有价值吗 | **13 句里有 4 句有明确价值**（06:55 纠错、13:30 发现文档不一致、13:55 替用户改完文件、11:45 审核结论）。其余 9 句是复述进度、重复、陪伴寒暄 | 实测，逐条阅读 |
| 平均有效率 | **约 30%** | 推断，基于上表 |
| 真正的价值在哪 | 不是"陪伴"，是**「高准确率的一次性事实核查 + 文档整理 + 只读取证」**。这些恰好是它现在做得最好的事 | 推断 |
| 用户为什么还在用它 | 因为 30% 的那几件事确实省事。但用户今天**主动发消息只有 1 次**（07:09 追问），说明还没形成依赖 | 实测：`conversation.jsonl` 今日 user 仅 1 条 |

### 2.3 一个必须承认的反例

用户 10-11 在 GUIDE.md 里留下的原话（现在仍生效）：
- 「汇报要报**帮上了什么**，不要报**你正在干什么**」

这说明画像写进去了，但没约束住输出。

## 3. 最大的三个技术债 / 结构性风险

### 风险一：`offer` 无需用户同意即自动执行 —— 与全部文档承诺相反【最高优先级】

| 项 | 内容 |
|---|---|
| 位置 | `src/openlookout/sprite/proactive/live.py:367-389` |
| 机制 | `tick()` 读到 `offer.json` 里 `kind == "offer"` 且状态不在终态集合中，就 `record_offer_result(offer,"auto_started")` 并起线程跑 `run_offer`，**中间没有任何用户交互** |
| 文档承诺 | `README.md`（AGENTS.md）:9「**用户点头才动手**」；`AGENTS.md` 硬规则 1「动手的事必须先写撤回方式」；`docs/product_strategy_active_assistant_research.md` §3.1「低风险：第一阶段只做只读、草稿、导航或提醒」 |
| 实测影响 | `offers.jsonl` 有 **54 条 `auto_started`**，全部 `options` 为空 = 从未征询过。其中包含「C盘快满了，要我清一下吗？」这种**疑问句**被直接当成指令执行 |
| 为什么没被发现 | 现象与"用户主动点了好的"在日志里长得一样（都是 auto_started）；且这条路最后一次触发是 **10-11 15:22**，之后模型全在出 companion，这条路径静默了两个自然日 |

**这不是 bug，是设计与文档的正面冲突。** 修法只有两种：要么恢复成必须点击，要么改掉全部文档措辞。现状是最坏的 —— 代码做 A，文档说 B。

### 风险二：去重闸对 `companion` 几乎不生效，导致同一件事连说 4 次

| 项 | 内容 |
|---|---|
| 位置 | `src/openlookout/vista/benchmarks/desktop/session.py:183` |
| 机制 | `allowed = conversation_worth_saying(say) if kind == "companion" else worth_saying(topic, kind, say)` |
| 问题 | `companion` 走的是 `help.py:135` 的 `conversation_worth_saying()` —— 它**只比对最后一条对话的文本是否完全相同**，没有 topic 归并、没有冷却窗口。而 `offer` 走 `worth_saying()`，有 `COMPANION_COOLDOWN_S=600` 的时间窗和 topic 匹配（`help.py:88-132`） |
| 实测证据 | 今日实验6「14→13」被说了 **4 次**（06:55 / 07:01 / 07:04 / 13:46）。这 4 条的 `topic` 分别是 `''`、`实验6提交`、`实验6`、`实验6` —— **topic 每次都被模型现编一个新值**，字符串匹配自然拦不住 |
| 放大因素 | 全量 320 条中 **169 条（52.8%）topic 为空**。`help.py:158` 的 `_fingerprint()` 兜底只在 `worth_saying()` 里用，而 companion 路径根本不走那里 |
| 讽刺之处 | `help.py:6` 的注释明确写着「真实数据里曾出现过同一句连发 4 次——这不是关心，是骚扰」。**同一个 bug 换了个入口复发** |

**结论：去重机制存在，但只在 `offer` 一条路上生效；而 2026-10-12 之后的真实流量 100% 是 `companion`。** 换句话说，那条纪律在当前版本是空转的。

### 风险三：`brain.py` 承载了过多职责，且已被并行编辑损坏过

| 项 | 内容 |
|---|---|
| 规模 | `brain.py` **1408 行 / 80KB**，`actions.py` **1652 行 / 93KB**。AGENTS.md 把 brain.py 列为"小精灵的大脑"，实际它同时是提示词仓库、事实线接线、协议校验、上下文裁剪、传输层适配 |
| 事故记录 | `STATUS.md` 第 74 行自述：brain.py 今天 06:48/06:57 两次被并行编辑成语法错误/NameError 中间态，常驻 brain 出现 crash loop |
| 现场残留 | 磁盘上现存 **4 份 brain.py 残留**：`brain.py.broken-0820`、`brain.py.work-20261013-083250.bak`、`-083609.bak`、`-090512.bak`。其中 2 份**已被 git 跟踪**（`.gitignore` 的 `brain.py.broken-*` / `brain.py.work-*.bak` 规则加得太晚，没拦住已入库的） |
| 后果 | 常驻进程靠 mtime 热重启（`live.py` 每 2 秒检查）。一个 1408 行文件被并发写入时，运行中的实例可能加载到半成品 |
| 并行成本 | AGENTS.md「铁律四条」承认 10-13 有"两个 agent 同时写 brain.py 互相覆盖，烧掉四十分钟"的事故 |

**建议**：brain.py 至少拆成 `prompts.py`（纯文本，好 diff 好回滚）/ `facts.py`（三路事实接线）/ `protocol.py`（next_step 校验）。提示词和逻辑混在一个文件里，是并发事故的直接成因。

### 6.2 综合判断

| 口径 | 数字 | 说明 |

**我给出的诚实数字：产品完成度约 35%。**

1. 唯一一条真正改变用户处境的路径 —— 用户同意后执行 —— **在真实数据里从未发生过，且当前代码还走的是相反方向**。这不是"还没测"，是"链路入口不存在"。
2. 78 句输出中约 30% 有价值，核心价值来自"事实核查 + 文档整理"这类**一次性任务**，而不是"持续陪伴"。产品定位事实上已经漂移到了一个更窄、更实在的东西上。

如果非要给一个更低的数字：按"能不能被一个不认识这个项目的人用起来"衡量，**约 25%**。
