## 一、一句话诊断

**这个项目不缺功能，缺的是一个能对「这句话/这个动作值不值得做」负责的价值闸——而用户已经把这条要求用原话写在 `GUIDE.md` 里了。**

支撑这个判断的三个事实，全部来自运行时数据而非文档自述：

1. **说得太多、太长、太像旁白。** 40 小时 291 条开口；10-11 单日 245 条 ≈ **每 6 分钟一次**；气泡长度中位 **124 字**（用户要求「60 字上下」），达标率 **13.7%**；在他提意见的当天，`offer` 类气泡 **147/147 全部超 60 字**。同一句「C盘快满了，要我清一下吗？」**连发 9 次**。
2. **真正在跑的，是仓库里最小的那条线。** 主线 `vista/benchmarks/desktop/` 约 5,641 行且**在 git 里 0 个文件**；而 `src/openlookout/sprite/` 22,152 行——全项目最大——**不在运行路径上**。⚠️ **本条第 2 句已被第二轮实测证伪，见上方更正 E1；两个行数也已作废（E3）。**
3. **安全论据评的不是会动手的那条路。** `eval_all` 的 461 陷阱 / 0 误操作**是真的**（redteam 已复现），但它跑在 `tempfile` 沙箱里、用 `FakeController`，评的是 `sprite/` 那条线；而真正会改用户机器的 `desktop_end_process` / `desktop_suspend` / `desktop_tidy` 在 `actions.py` 里，**没有任何对抗用例覆盖**。

## 二、必须接受的三个事实

### 事实 1：仓库里有三个产品定义，没有任何一处说明哪个是当前的

| 文档 | 它描述的产品 | 状态 |
|---|---|---|
| `AGENTS.md` | 常驻看屏幕 → 模型判断 → 开口提议 → **用户点「好的」才动手** | 与运行时拓扑一致 |
| `docs/PROACTIVE_AGENT.md` | 「**能做的全部直接做**」「**没有提问流程**」「不是 LLM 一直盯着屏幕」 | **未接入运行路径**，且与上一条直接冲突 |
| `src/openlookout/README.md` | 从行为痕迹挖未察觉需求 → 交出**已验证方案**（HTML 卡） | 另一条产品线，未在运行 |

这不是文档瑕疵，而是**路线图会按错的文档做取舍**。任何「按 PROACTIVE_AGENT.md 去实现直接做」的路线都会同时引爆下面两条已经在流血的风险。

**处置**：一份文档只留一条线。把 `PROACTIVE_AGENT.md` 明确标注为「历史设计（未接入当前运行路径）」，并在每份文档头部加一行「本文档对应的代码入口 + 采集时间」。

### 事实 2：用户已经给出了验收标准，系统记录了但没执行

`sprite_home/companion/GUIDE.md`（3,283 字节，10-12 07:18 写入）——**注意：`STATUS.md:102` 自述「画像仍是初始值/空的」是错的**，redteam 与 Lead 各自独立核实过。它里面有用户逐条给出的产品要求，最有分量的一段是：

> - **别做指标触发的条件反射**：看见内存高就去 trim、看见文件多就归档，这种"没有战略理解"动作他明确点名为反面例子。
> - 主动性要落在两件事上：①自己去找"哪些场景我真能派上用场"；②派上用场前先有全局排序——这件事此刻值不值得做、为什么要做，比做本身重要。
> - 所以每次动手前先自问一句：这个动作服务的整体目标是什么？答不上来就不要动，宁可 quiet。

**这段话就是本项目的产品验收标准**，而且比仓库里任何一份设计文档都更精确。

问题是：**画像写进去了，但没有治理行为。** 60 字要求落库之后，气泡反而变长（§一.1）。这是「说了不听」——信任问题里最难修的一种。

### 事实 3：真正的风险不在「提议失败」，在「未覆盖的动手路径」

Lead 的初稿曾据 `offers.jsonl` 的 `action` 字段判断「系统几乎从不动手」。**这是错的**，redteam 给出了反证：

- `offers.jsonl` 是**对话**账本，不记录 `desktop_*` 工具路径；
- 真实改动确实发生过：`undo.jsonl` **7 条**（含一次「整理桌面 **79 个文件**」）、`quarantine/restore_map.jsonl` **277 条**（`held` 272、201.1 MB、**240 条原始路径已不存在**）；
- 而 `desktop_end_process` 直接 `terminate()` + `kill()`，撤销方式是 `relaunch`——**只能重启进程，不能恢复未保存的内容**，且零对抗用例覆盖。

**正确结论：动了手，但账本没记，且动手路径没被评测。** 这比「什么都不做」严重得多。

## 三、收敛决策：一条主线，两个挂件

这是本文最重要的工程判断。

### 现状：两条线各有一半，且互不连接

| | 感官（看屏幕） | 嘴（说话） | 手（改机器） | 安全层 | 评测 | 版本控制 |
|---|---|---|---|---|---|---|
| **主线** `vista/benchmarks/desktop/` | ✅ 有 | ✅ 有 | ⚠️ 有但无闸门 | ❌ 无 | ⚠️ 只测不碰真机 | ❌ **0 文件入 git** |
| **休眠线** `src/openlookout/sprite/` | ❌ 无 | ⚠️ 旧通道 | ✅ 有 | ✅ **有** | ✅ **461 陷阱** | ⚠️ 部分 |

**主线有眼睛和嘴，没有刹车和保险；休眠线有刹车和保险，没有眼睛和嘴。**

### 决策

> **把休眠线的闸门接到主线的感官和嘴上。主线保留，休眠线降级为「动作库 + 安全层」，`lookout/` 报告线归档。**

具体三条：

1. **保留并强化 `vista/benchmarks/desktop/`** 作为唯一产品主线——它是唯一有真实感知、真实用户反馈、且当前在跑的线。
2. **把 `sprite/risk.py` 的分类器、隔离区机制、`eval_all` 对抗评测接入主线的 `actions.py`**——这是全项目唯一被对抗验证过的安全层，浪费它是最大的沉没成本。
3. **归档 `lookout/`（v1 洞察报告线，6,328 行）与 `lookout/pet.py`**——它是另一个产品（异步行为洞察 + HTML 报告），不是桌面小精灵。保留代码与文档，从主线移除入口，不再投入。

### 为什么不是反过来（按 `PROACTIVE_AGENT.md` 重做主线）

因为那条线的核心主张是「**直接做、不要问**」，而它的证据基础（461/0 误操作）**评的不是会动手的代码**。在闸门建好之前执行这个主张，等于在用户真实桌面上跑一个没有对抗评测覆盖的自动执行器——而 `desktop_end_process` 已经证明那条路上有不可逆操作。

## 四、路线图：五个阶段，每阶段一个可证伪的门

原则：**每个阶段的验收都必须是一个能用命令跑出来的数字**，不能是「感觉好多了」。

### M0 · 止血（1–3 天）——不加任何新功能

| # | 做什么 | 为什么现在 | 门（可证伪） |
|---|---|---|---|
| 0.1 | **把核心代码提交进 git**（`vista/` 目前 `git ls-files` = 0，22,684 行无版本控制） | 同类事故**已经发生过一次**：`reading.py` 被误删且从未入库，**永久不可恢复**，日志里 `ImportError: cannot import name 'reading'` 至今可见 | `git ls-files src/openlookout/vista` 非空 |
| 0.2 | 修 `auto_failed` 记账：`returncode:0` 不得计为失败 | 36/36 条均为假失败，污染了唯一的成功指标 | 新增 `auto_failed` = 0 且原因为真实错误 |
| 0.3 | 把「≤60 字」和「24h 内同 topic 不重复」从**提示词**变成 `help.publish()` 前的**硬闸**，并记录拦截计数 | 用户已明确要求；提示词版本达标率 13.7%，且同一句连发 9 次 | 新增气泡长度 **P50 ≤ 60**；重复文本 = 0；**且拦截计数 > 0**（证明闸门在工作，不是模型恰好安静） |
| 0.4 | 加**数字闸**：气泡中出现 GB/%/进程名时，必须能在本轮工具返回里找到出处 | `GUIDE.md:16` 记录用户曾纠正「C盘剩 0.6G」是错的；10-11 10:33 的提议仍写「C 盘要跌破 5G 了（5.79，几分钟掉 1.7G）」 | 无出处的数字气泡 = 0 |

> 0.1 必须在 0.2–0.4 之前：否则后面所有工作都建在一份可被一次误删抹掉的代码上。

### M1 · 可测量（1 周）——让「有没有变好」可计算

| # | 做什么 | 门 |
|---|---|---|
| 1.1 | `offers.jsonl` 增加三态：`accepted` / `rejected` / `ignored_by_timeout`（GUI 已有按钮，落库即可） | 能跑出一条 SQL/脚本报出「过去 7 天接受率 = X%」 |
| 1.2 | 冻结三个指标定义：**打扰率**（每活跃小时开口数）、**接受率**、**留存**（连续运行天数） | 三个指标各有定义、及格线、计算脚本 |
| 1.3 | 决策延迟打点：每回合记录端到端耗时与模型段数，输出 P50/P95 | 能报出延迟分位；当前基线是单段中位 15s、最大 201.9s |
| 1.4 | 统一账本：让 `desktop_*` 动作同时写入对话账本与动作账本 | 「系统做了多少事」一次查询可得 |

**现状基线（供对比）**：`feedback.jsonl` 仅 **8 行**、291 提议对 8 反馈 → **接受率目前无法计算**。M1 不完成，M2 的效果就无法判断。

### M2 · 价值闸（2 周）——核心，也是用户原话要求的那一层

单一闸门，**说话和动手都必须先通过**。模型在动作/开口前必须填出一个结构化记录：

```
serves_goal     这个动作服务的整体目标是什么？   ← 用户原话要求的那一问
evidence        本轮工具返回里的具体证据是什么？
expected_value  预期省下什么 / 避免什么？
cost            打扰成本 + token + 可逆性
```

**任一为空 → 强制 `quiet`。**

| # | 做什么 | 门 |
|---|---|---|
| 2.1 | 实现闸门，落点在模型输出之后、`publish()` 之前 | 每轮决策记录含上述四字段；为空则 quiet |
| 2.2 | 把 `GUIDE.md` 的偏好**编译成机器可校验策略**（长度、去重、数字来源、静默处理内存类），而不是塞进提示词 | 偏好违反率可统计且为 0 |
| 2.3 | 保留「反馈只作权衡」：模型可以否决用户明说的偏好，但**必须记录理由**（对应愿景里的「快马 → 汽车」） | 每次否决留下可审计的理由行 |

**门**：开口率从 **33%** 降到 **< 10%**，**且**接受率上升。必须同时看两个数——只看开口率会退化成「什么都不说」。

### M3 · 让手接上（2–3 周）——补上「帮忙」那一半

| # | 做什么 | 门 |
|---|---|---|
| 3.1 | 把 `sprite/risk.py` 分类器 + 隔离区 + `eval_all` 接入主线 `actions.py` | 所有会改用户机器的工具都在同一条闸门之后 |
| 3.2 | `desktop_end_process` 二选一：**补闸门 + 对抗用例**，或**从模型可见工具表里移除** | `eval_all` 的陷阱集包含 `end_process` 用例，且 `procctl.py` 与 `actions.py` 的不变量声明不再互相矛盾 |
| 3.3 | 端到端跑通一次「发现 → 判断 → 动手 → 汇报 → 撤销」 | 有真实会话记录 + 撤销日志，且**不询问**（符合用户「先做完再汇报」要求） |
| 3.4 | 只挑**一个**场景做深，不做场景扩张 | 该场景连续 7 天真实使用，接受率有数 |

|---|---|---|

## 五、明确「不做」

1. **不做「直接做、不要问」**（`PROACTIVE_AGENT.md` 的主张）——在 M2/M3 完成前，它会同时引爆打扰与不可逆两条已流血的风险。
2. **不做场景扩张**。现有场景没有一个是端到端验证过的；每加一个场景都在放大 R1（打扰）。
3. **不做本地小模型 tier1**。延迟瓶颈在**模型通道 TLS 重试**（最近一小时 98 次 SSLEOF、102 次重试），不在模型选择。先修通道。
4. **不做跨平台 / 不做安装包**，直到 M3 门通过。
5. **不做「常驻截图」的扩大**。当前已本地囤 **2,040 张截图 / 257.3 MB**，且全屏逐帧 base64 上传、**零遮挡逻辑**——隐私是公开即引爆的风险（R3），不是可以后置的工程细节。

## 六、如果只能保留一条红线

> **在「这句话值不值得说」这件事上，模型不得拥有最终裁定权——必须由代码用可测的数字先否决，模型只能在通过闸门后决定说什么。**

理由：它是唯一一条**用户已经把验收标准写在纸上**的要求（`GUIDE.md`：60 字、不要定时配额、标准是「值不值得说」）；它是唯一一个**已经发生、且会直接导致卸载**的失败模式；而且它**可测、不会自欺**——气泡长度 P50、重复文本数、拦截计数，跑一遍 `offers.jsonl` 就有。

## 七、怎样判断这份路线图失败了

写清失败条件，避免自我说服：

| 检查点 | 失败信号 | 该怎么办 |
